# Push notifications and Live Activities

Push identity belongs to a device session, not to a user. The iOS app keeps a stable device ID, registers with APNs, observes ActivityKit's push-to-start token, and sends both tokens plus this device's preferences through `UpdateDevicePushSettings`. One user may therefore have many independently configured phones. Signing out deletes that device row; account erasure deletes every device and Live Activity token through foreign-key cascades.

The settings sheet controls ordinary sleep-change notifications, Live Activities, and the sleep-reminder lead time for this phone. The backend always applies the stored switches while selecting family devices. Do not turn these into user-wide preferences.

Starting or ending sleep writes an `activityStart` or `activityEnd` delivery into the SQLite outbox in the same transaction as the command and sync event. A backend worker claims due rows, retries transient APNs failures with bounded backoff, and clears tokens Apple reports as invalid. The initiating phone starts and ends its activity locally; other enabled caregiver phones receive a push-to-start request. Each resulting activity uploads its rotating activity push token so the backend can end it later. Uploading a push-to-start token atomically queues durable reconciliation for any sleep already active when the device signed in or enabled the feature. The worker rechecks active sleep, child visibility, current membership, device preferences and the latest token before sending; an ended sleep never replays an old start.

Foreground freshness is cursor-driven. While the scene is active, the timeline first runs `Sync`, then holds one `WatchFamily` Connect stream open as an invalidation channel. A stream message, expiry, transport failure, or foreground transition always leads back through `Sync` before another stream is opened. The stream closes when the scene backgrounds; iOS does not allow an ordinary application network stream to remain open indefinitely while suspended.

Each sleep transition also sends a separate silent APNs background notification to other family devices, even when visible alerts are disabled. The payload contains only `content-available` plus the family identifier, uses APNs background priority, and causes the app delegate to run the same authoritative sync during the system's short wake window. A `BGAppRefreshTask` resynchronizes all locally known families as a discretionary fallback. Both mechanisms are best effort and may be delayed or throttled by iOS, so correctness must never depend on them: every foreground activation synchronizes before waiting on the stream.

APNs alert pushes use topic `solutions.bytesized.uneton`; ActivityKit pushes use `solutions.bytesized.uneton.push-type.liveactivity`. Configure `UNETON_INTEGRATION_APNS_TEAM_ID`, `UNETON_INTEGRATION_APNS_PRIVATE_KEY_ID`, `UNETON_INTEGRATION_APNS_PRIVATE_KEY_PEM`, and `UNETON_INTEGRATION_APNS_TOPIC` when using a dedicated APNs provider key. If all four are omitted, the backend reuses the Sign in with Apple key and bundle ID, which only works when that key is also enabled for APNs. Keep the development and production device-token environments distinct. `UNETON_APNS_ENVIRONMENT` supplies both the app entitlement and its runtime Info.plist value (Debug development, Release production); verify the exported signed app uses the same environment.

ActivityKit tokens rotate. Always iterate `pushToStartTokenUpdates`, `activityUpdates`, and each activity's `pushTokenUpdates`; never cache a token as permanent identity. A Live Activity shown by iPhone may also be presented on its paired Apple Watch by the system. The Watch app does not register a separate ActivityKit token.

## Remote sleep reminders and local fallback

`UpdateDevicePushSettings` accepts a device notification language (`en`/`fi`) and an absolute `remote_reminders_until` timestamp. An epoch timestamp disables ownership. The server acknowledges ownership only when APNs is configured, a device token exists, and ordinary notifications are enabled. Requests are bounded to 24 hours plus five minutes of clock tolerance. Devices that never request ownership continue using local reminders. A new ownership period starts at server registration time; it cannot backfill a window previously covered locally. Renewing a still-active period retains its original start.

The iPhone persists the maximum attempted ownership deadline before cancelling its local notification and issuing the RPC. It serializes settings updates and retains that deadline after an ambiguous response. The local scheduler only accepts fire times at or after the deadline; a successful response can release ownership when remote delivery is unavailable. Sync and push registration renew ownership. This avoids a lost registration response causing duplicate local and remote alerts. It does not use local fallback to compensate for a missed APNs push inside the owned period, and cannot guarantee delivery while the app remains closed beyond that period. Offline fallback uses the most recent acknowledged forecast, cancels for locally sleeping babies, and may be stale when another caregiver has changed the diary without this device syncing.

The push worker reconciles a durable `sleep_reminders` schedule every 30 seconds from acknowledged records for every eligible baby and device. It keys each reminder by device, baby, and last completed sleep, so revising an estimate or lead time updates the same pending reminder and never repeats an attempted wake episode. Sleeping babies, provisional/missing estimates, disabled notifications, removed membership, expired ownership, and stale windows suppress delivery. Before each due submission the worker recomputes and validates eligibility in one SQLite snapshot and durably claims the attempt. Reminders use a five-minute grace/expiry capped by ownership and the target (zero lead allows the five-minute grace at the target). They are generic English/Finnish alerts with no diary-state payload; they never move the sync cursor. Neither the scheduler nor the client applies push-derived state.

A claim precedes network I/O. There is one APNs submission attempt per wake episode and no retry after an ambiguous failure or worker crash; that choice avoids duplicate planning nudges but may miss one. APNs cannot retract an already submitted alert after a concurrent diary edit. Seven-day schedule cleanup runs during reconciliation, and account/device/family removal cascades delete rows. A restore follows the existing generation-rotation procedure; the worker suppresses historical reminders outside the five-minute grace. Verify real-device delivery and suspension separately from unit and integration tests.

## Token registration and failure recovery

The phone captures APNs callbacks even if they precede SessionStore initialization. It keeps the latest device tokens and pending activity registrations in device-only, after-first-unlock Keychain storage, alongside a persisted increasing registration counter. Work is written and verified before upload. The authenticated user scopes activity work; switching users drops old activity work and sign-out clears the registration record. Each running activity has an independent observer for its token and lifecycle, with duplicate discovery suppressed. Existing activities are rediscovered on launch, and observation ends when an activity ends or is dismissed.

A single activity uploader drains latest-value work. It acknowledges only the token and revision actually sent, retaining rotations that arrive in flight. The ordinary device-settings uploader remains serialized. Successful Sync, authentication/foreground restoration, token callbacks and a cancellable backoff task retry registration. Backoff grows from two seconds to five minutes and refreshes authentication through the usual control-plane path. iOS may suspend this timer; persistent work resumes on the next available launch or wake. A locally started sleep can produce a token before its durable command is acknowledged; the token stays queued until registration succeeds. Local reconciliation after Sync ends obsolete or duplicate presentation without applying ActivityKit state to the diary.

The backend compares persisted registration revisions inside the registration transaction. A stale request returns `aborted` and cannot overwrite a newer device token, preference or activity token. Activity revision watermarks remain in `live_activity_starts` after token cleanup, so an older request cannot resurrect a removed token. Registering a token for an already ended/deleted/superseded sleep atomically queues a device-targeted end; repeated registration before delivery coalesces that job. Successful or invalid end delivery deletes only the exact token attempted, preserving a rotation received during network I/O. End jobs briefly wait (15 minutes from start claim) for missing remote activity tokens; a token arriving later creates a fresh durable end job.

On worker restart, unconfirmed start claims associated with interrupted sending jobs are released before those jobs retry. Confirmed activity registrations remain protected. Remote starts use at-least-once recovery: an ambiguous APNs response or interrupted worker can cause a duplicate start, since APNs acceptance is not an exactly-once display acknowledgement. The next Sync removes duplicate local presentation. APNs and iOS background runtime remain best effort; neither a token registration nor an accepted push proves display on a locked phone.

Client diagnostics report registration failures, pending counts and oldest pending age; backend diagnostics retain APNs rejection reasons and delivery retry attempts. They do not log raw tokens or child content. Real-device verification requires two signed-in physical phones: background/locked remote start and end, multiple babies, token rotation, offline registration, relaunch, disabled Live Activities and caregiver removal.
